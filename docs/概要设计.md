## 1 引言

### 1.1 编写目的

本文说明 des-engine 的总体结构、功能划分、对外接口、运行方式和数据组织，供评审和后续详细设计使用。程序内部算法、字段和伪代码见 [详细设计说明书](详细设计.md)。

### 1.2 背景

des-engine 是一个用 Go 编写的离散事件仿真引擎。其他 Go 模块通过包引用使用它，而不是把引擎做成独立业务系统。

- 软件名称：des-engine
- 模块路径：`github.com/cgcodeboy/des-engine`
- 语言版本：Go 1.25
- 依赖：仿真内核使用 Go 标准库。指标 HTTP 使用 [Gin](https://github.com/gin-gonic/gin)

### 1.3 定义

| 术语 | 含义 |
| --- | --- |
| 仿真时间 | 引擎内部时间。单位是毫秒，用整数表示 |
| 步长 | 固定为 1ms。一个步长对应一个桶 |
| 桶 | 同一毫秒上的事件集合。桶下标等于该毫秒的时间戳 |
| 水位 | 已经关闭的仿真时间上界。早于水位的事件被拒绝 |
| 当前步长队列 | 正在执行的这一毫秒里，尚未执行完的事件队列 |
| 真实模式 | 每个桶开始前，墙钟对齐到该桶的理论时刻 |
| 追赶 | 墙钟已经晚于理论时刻时，不再等待，立即执行该桶 |
| 慢事件 | 处理函数的墙钟耗时大于 1ms 的事件 |
| 链式触发 | 当前毫秒执行期间插入的同桶事件，追加到当前队列尾部并在本毫秒内继续执行 |

## 2 总体设计

### 2.1 需求规定

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R1 | 包引用 | 外部模块引用 `engine` 与 `metrics` |
| R2 | 生命周期 | 支持启动、停止、等待结束。重复停止无副作用 |
| R3 | 固定步长 | 时间按 1ms 分桶，按桶下标从小到大执行 |
| R4 | 动态插入 | 运行前和运行中都可以插入事件。当前毫秒内的新事件在本毫秒末尾链式执行 |
| R4a | 未来事件 | 调用方给出事件和延迟。引擎立即收下，并在延迟到达后的仿真时刻触发该事件 |
| R5 | 因果 | 拒绝早于当前水位的事件 |
| R6 | 真实时间 | 默认按墙钟对齐。滞后时追赶，并交出滞后信息 |
| R7 | 并发 | 未来桶、当前队列和状态用互斥锁保护，用条件变量等待 |
| R8 | 慢事件 | 处理函数墙钟耗时超过 1ms 时写日志，并能从指标接口看到是哪些事件 |
| R9 | 异步日志 | 事件执行路径不发生日志 IO |
| R10 | 指标 | 提供健康检查、JSON 状态和 Prometheus 文本 |

### 2.2 运行环境

- 操作系统：可运行 Go 1.25 程序的环境
- 部署形态：库。指标 HTTP 由调用方随进程一起启动
- 持久化：无。状态只存在于进程内存

### 2.3 基本设计概念和处理流程

仿真时间的整数 `k` 同时是第 `k` 毫秒和桶 `k`。没有事件的桶不逐个空转，引擎直接推进到下一个有事件的桶。

真实模式下，桶 `k` 的理论墙钟时刻是 `origin + k * 1ms`。

1. 墙钟未到理论时刻时，引擎等待。等待可被停止、上下文取消，或一个更早且尚未关闭的新桶打断。
2. 墙钟已晚于理论时刻时，引擎立即执行该桶，把滞后交给回调和日志。后续桶在重新追上之前同样不再补等。
3. 执行该桶时，处理函数可以向当前毫秒追加事件。这些事件排在当前队列尾部，并在进入下一毫秒之前执行。
4. 该毫秒的队列排空后，水位前移，这一毫秒关闭。

未来事件由调用方同时给出事件内容和延迟。引擎立刻返回事件标识，不阻塞到触发时刻。触发时刻按当前仿真时间加上延迟计算，再向上取整到毫秒。真实模式没有滞后时，该毫秒的理论墙钟时刻就是调用之后相应的墙钟时间，引擎等到那个时刻再执行。引擎处于追赶状态时，仿真时间走得比墙钟快，事件仍在算得的仿真毫秒执行，墙钟上可能早于“再等一段延迟”。

事件处理函数和滞后回调可以再次插入事件。二者都不能做 IO，也不能调用停止或等待，否则会阻塞 1ms 步长，或与事件循环形成等待环。

### 2.4 结构

```text
调用方
  │
  ├── engine          仿真内核
  │     ├── 事件循环
  │     ├── 慢事件记录
  │     └── internal/bucket      未来桶
  │     └── internal/asynclog    引擎日志队列
  │
  └── metrics         指标与 HTTP
        └── internal/asynclog    指标服务日志队列
```

`engine` 不引用 `metrics`。`metrics` 只读取 `engine` 的快照，不把状态写回引擎。两个异步日志队列相互独立。

仓库根目录不放置 Go 源文件。源码按包分目录，设计文档位于 `docs/`。

### 2.5 功能需求与程序的关系

| 需求 | engine | internal/bucket | internal/asynclog | metrics |
| --- | --- | --- | --- | --- |
| R1 包引用 | 是 | 否 | 否 | 是 |
| R2 生命周期 | 是 | 否 | 是 | 是 |
| R3 固定步长 | 是 | 是 | 否 | 否 |
| R4 动态插入 | 是 | 是 | 否 | 否 |
| R4a 未来事件 | 是 | 是 | 否 | 否 |
| R5 因果 | 是 | 否 | 否 | 否 |
| R6 真实时间 | 是 | 否 | 是 | 否 |
| R7 并发 | 是 | 否 | 是 | 否 |
| R8 慢事件 | 是 | 否 | 是 | 是 |
| R9 异步日志 | 是 | 否 | 是 | 是 |
| R10 指标 | 是 | 否 | 否 | 是 |

`internal/bucket` 只保存未来桶，不加锁。锁由 `engine` 持有。

### 2.6 人工处理过程

无。本软件没有需要人工值守的业务步骤。运行观察通过日志和 HTTP 指标完成。

### 2.7 尚未解决的问题

下列内容不进入本版本：

- 并行离散事件仿真
- 协程形式的进程层
- DEVS 耦合模型
- 内置资源队列库
- 检查点与恢复
- 可配置步长或墙钟倍速

## 3 接口设计

### 3.1 用户接口

本库没有图形界面。调用方通过 HTTP 观察运行状态。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /healthz` | 指标服务是否在监听 |
| `GET /status` | JSON 快照，包含最近的慢事件 |
| `GET /metrics` | Prometheus 文本，包含慢事件累计次数 |

`/metrics` 不使用事件名称作为标签。具体是哪些事件超过 1ms，以 `/status` 为准。字段定义见详细设计说明书。

### 3.2 外部接口

外部 Go 模块使用：

```go
import (
    "github.com/cgcodeboy/des-engine/engine"
    "github.com/cgcodeboy/des-engine/metrics"
)
```

`engine` 提供引擎的创建、启动、停止、按绝对时间插入、按延迟插入未来事件、取消和快照。未来事件的入口是 `AddFuture(after, event)`。`metrics` 提供按上下文启动和关闭的 HTTP 服务。函数签名、延迟取整和错误见详细设计说明书第 3.6 节与第 3.8 节。

### 3.3 内部接口

| 提供方 | 使用方 | 接口内容 |
| --- | --- | --- |
| `internal/bucket` | `engine` | 放入未来桶、取下一个桶、拿走某一桶的事件 |
| `internal/asynclog` | `engine`、`metrics` | 非阻塞写入日志，停止后排空 |
| `engine.Snapshot` | `metrics` | 只读快照，供 JSON 和 Prometheus 文本使用 |

## 4 运行设计

### 4.1 运行模块组合

一次典型运行包含：

1. 调用方创建 `engine`。
2. 调用方启动引擎。引擎协程按桶执行事件。
3. 引擎的日志协程负责写出日志。
4. 需要观察指标时，调用方再启动 `metrics`。指标服务拥有自己的日志协程。

引擎可以在不启动 HTTP 的情况下独立运行。

### 4.2 运行控制

| 操作 | 结果 |
| --- | --- |
| 启动 | 事件循环进入运行。重复启动失败 |
| 停止 | 当前处理函数返回后退出循环，再排空日志。重复停止无效果 |
| 等待 | 阻塞到循环结束且日志排空完成 |
| 上下文取消 | 与停止相同 |
| 空闲退出 | 仅在调用方打开该选项、且没有待处理事件时结束 |
| 时间上限 | 不执行上限之后的桶 |

默认在没有事件时继续等待新事件，不自动退出。

### 4.3 运行时间

- 仿真步长固定为 1ms。
- 真实模式默认开启。桶 `k` 对齐 `origin + k * 1ms`。
- 慢事件阈值固定为 1ms，比较的是处理函数墙钟耗时。
- 关闭真实模式后，循环不按墙钟等待。该模式用于测试。

## 5 系统数据结构设计

### 5.1 逻辑结构设计要点

| 数据 | 内容 |
| --- | --- |
| 事件 | 标识、名称、仿真时间、处理函数、取消标记 |
| 未来桶 | 按毫秒分组、组内按插入顺序排列的事件 |
| 当前步长队列 | 正在执行的毫秒中尚未完成的事件 |
| 慢事件 | 标识、名称、仿真时间、墙钟耗时、超出量、完成时刻 |
| 快照 | 状态、仿真时间、队列规模、计数、滞后、慢事件列表 |

### 5.2 物理结构设计要点

全部数据位于进程内存。

| 数据 | 组织方式 | 容量 |
| --- | --- | --- |
| 未来桶 | 映射加最小堆 | 随未执行事件增长 |
| 当前步长队列 | 队列 | 随当前毫秒的事件数增长 |
| 慢事件 | 环形缓冲 | 最近 128 条 |
| 日志队列 | 通道 | 4096 条 |
| 指标 | 无独立存储 | 读取时从快照生成 |

慢事件总数和日志丢弃数在列表被截断后仍然累加。

### 5.3 数据结构与程序的关系

| 数据 | 写入 | 读取 |
| --- | --- | --- |
| 未来桶、当前队列、水位 | `engine` | `engine` |
| 慢事件环 | `engine` | `engine` 快照，再由 `metrics` 输出 |
| 引擎日志队列 | `engine` | `internal/asynclog` |
| 指标日志队列 | `metrics` | `internal/asynclog` |

## 6 系统出错处理设计

### 6.1 出错信息

| 类别 | 表现 |
| --- | --- |
| 插入非法 | 向调用方返回错误。包括空名称、空处理函数、过期时间、引擎已关闭 |
| 重复启动 | 向调用方返回错误 |
| 处理函数失败 | 引擎停止，等待操作返回该错误 |
| 处理函数 panic | 引擎恢复 panic，停止运行，等待操作返回错误 |
| 日志队列已满 | 丢弃该条日志并计数。事件循环继续 |
| 停机时日志写不完 | 最多等待 2 秒，剩余日志计入丢弃数 |

### 6.2 补救措施

- 过期插入只拒绝该次调用，引擎继续运行。
- 处理函数失败后停止引擎，避免在错误状态上继续推进仿真时间。
- 日志丢弃不反压事件循环。丢弃数量可从指标接口观察。
- 本版本不提供自动重放、检查点或外部告警系统。

### 6.3 系统维护设计

维护信息来自两类输出：

- 异步日志：启动、停止、追赶、慢事件、处理函数错误。
- HTTP：`/healthz` 表示指标服务仍在监听；`/status` 和 `/metrics` 表示引擎状态。引擎停止后，`/healthz` 仍可返回成功，引擎是否在运行以状态字段为准。
